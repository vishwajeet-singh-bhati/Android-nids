1. Abstract

Mobile phones are now the main target for three everyday threats: malicious network activity (port scans, brute-force logins, denial of service), scam SMS that ask for OTPs or payments, and phishing links that imitate banks, couriers and login pages. Most protection tools send this data to a cloud service, which raises privacy concerns and needs a network connection.

Rakshak (Hindi: "protector") is an Android application that runs three independent AI detectors entirely on the phone:

  • Network intrusion detection. Rooted packet capture is turned into 147 connection and history features. An 18,913-parameter binary gate decides whether traffic looks suspicious, and a 173,721-parameter CNN–attention–LSTM model then estimates which of seven attack families it belongs to.
  • SMS scam detection. A two-tier cascade: a fast TF-IDF logistic-regression model with scam-evidence rules, then, only when needed, an INT8-quantized MobileBERT (22 layers). Archived test accuracy is 97.12% with smishing recall of 89.8%.
  • Phishing URL detection. A character-level CNN with 27 structural features and a character n-gram classifier, combined by a calibrated stacker into PHISHING / UNCERTAIN / LIKELY SAFE. Validation ROC-AUC is 0.976; the median on-device check takes 3.9 ms.

Links found inside incoming SMS are checked automatically. Every warning is shown immediately in plain language ("What happened / What you can do"). A local Llama 3.2 1B model (INT4) can then rephrase the advice, but it never decides the risk. The APK has no INTERNET permission, so messages and URLs never leave the device.

All models are exported with PyTorch ExecuTorch and run on the CPU through XNNPACK. Optimisations include post-training INT8 quantization (MobileBERT reduced from 87.5 MiB to 35.5 MiB with a 0.1 percentage-point accuracy change), cascade routing, a graph optimisation that cut network-detector latency by 25.3%, and a redesigned explanation prompt that made Llama guidance 5.4× faster. The report gives measured results with their test sets and states the remaining limitations openly.

2. Problem statement and objectives

2.1 Problem

Smartphone users in India receive a steady stream of fraudulent SMS: fake KYC updates, parcel re-delivery fees, prize and loan offers, and requests to "share the OTP with our agent". These messages usually carry a link to a look-alike website. Phones also join public and home Wi-Fi networks, where scans and login-guessing attacks can reach exposed services. Existing tools tend to:

  • cover only one threat (only SMS spam, or only web links);
  • send message text or browsing data to a server for classification;
  • show technical alerts that ordinary users cannot act on.

2.2 Objectives

  1. Detect suspicious network activity, scam SMS and phishing URLs on the device, without cloud inference.
  2. Keep models small and fast enough for a mid-range phone using quantization, cascading and graph-level optimisation.
  3. Give every warning in simple language, with a concrete next step, and make the optional LLM explanation safe (it may not change the decision).
  4. Measure honestly: separate offline benchmark, on-phone and synthetic test results, and report false positives and misses.
  5. Publish source code, training/export pipelines and evidence so that others can reproduce the work.

3. System overview

Rakshak has three detector pipelines that share one notification, history and explanation layer. Each detector has its own on/off switch. The network detector needs a rooted device to capture packets; the SMS and URL detectors work on a normal (non-rooted) phone.

4. Methodology

4.1 Network intrusion detection

Stage 1: reproduce a published baseline. We reconstructed the TSANet architecture [7] (CNN + self-attention + LSTM) on the CIC-IDS2017 dataset [1] with seven classes (Benign, Bot, Brute Force, DDoS, DoS, Port Scan, Web Attack), using a stratified 70/30 split (seed 42). Our reconstruction reached 97.03% accuracy, against the paper's 97.35%. We also reproduced the paper's 30% pruning variant.

Stage 2: add connection context. A single flow's statistics miss scan and brute-force patterns that only appear across many connections. We added 78 context features (counts and rates of recent connections per host, port and service). On the same split, accuracy rose to 99.98%, and benign false positives fell from 10,454 to 33.

Stage 3: align features with what a phone can measure. When we ran the model on a real phone, the offline features did not match what an Android device can observe. We therefore built a 147-input phone-aligned contract: 32 per-flow features plus 115 history features, computed identically by a Kotlin extractor on the phone and by a Python replay of the raw packet captures. The same packets now produce the same numbers on both sides; this is verified by hash-checked "golden" test rows.

Stage 4: cascade model.

  • Gate: MLP 147 → 96 → 48 → 1 that answers "is this connection suspicious?" (threshold 0.5408).
  • Diagnosis: CNN/attention/LSTM with context branch, 7 output classes. It runs only when the gate fires. If no class scores above 0.8, the alert is shown as "Unclassified" rather than forcing a guess.
  • Normalisation is embedded inside the exported model, so the app passes raw features.

Stage 5: real-phone data. We captured 20 verified sessions on our own Pixel 6a (normal browsing and controlled web attacks against our own lab server) and added them to training: 848 training, 184 validation and 184 test rows. Six training jobs of 40 epochs each were run, and the checkpoint was selected on validation data before the test set was touched.

Controlled phone testing. We tested the detector against live traffic from lab PCs that we own: port scans, FTP/SSH password guessing, application-level DoS/DDoS, bot-like beacons, and matched normal controls. An independent target-side log confirmed each attack, so an unrelated background alert is never counted as a detection.

4.2 SMS scam detection

Data. Two public corpora, the UCI SMS Spam Collection [2] and the LSDST-2022 smishing dataset [3], were merged and labelled into three classes: ham (normal), spam (promotional), and smishing (scam/phishing). 16,763 exact duplicates and 19 rows that leaked into the external set were removed. The data was then split by group into 4,055 train / 869 validation / 869 test rows, with a separate 27,885-row external set. Class weights (0.41 / 2.51 / 6.53) counter the imbalance.

Normalisation. Unicode NFKC, removal of zero-width characters, handling of look-alike characters and leetspeak, and lower-casing. Real URLs, e-mail addresses and phone numbers are extracted and replaced by placeholder tokens. The extracted URLs go to the URL detector.

Tier 1 (always runs). Word unigram + bigram TF-IDF (13,545 features) feeds a 3-class logistic regression. Evidence rules detect patterns such as OTP-sharing requests, payment-plus-threat, impersonation, prize, loan and parcel-fee lures, and obfuscation. Rules can raise risk (for example, "share your OTP with our agent" becomes smishing / high even when the linear model's top class is spam). Guarded routine messages such as genuine bank OTPs exit early as low risk.

Tier 2 (selective). MobileBERT [4] (22 bottleneck Transformer blocks, hidden size 512, 4 heads, 30,522-token WordPiece vocabulary, max 128 tokens) fine-tuned for 4 epochs (batch 16, learning rate 5e-5). The best checkpoint was chosen at epoch 3 on validation macro-F1 = 0.877. It runs only for messages that are not clearly ham, that triggered a rule, or that contain a link. A rule-governed fusion keeps strong Tier 1 evidence and never downgrades a high-risk finding.

4.3 Phishing URL detection

Data. Phishing URLs come from PhishTank and OpenPhish feeds. Benign full URLs were sampled from the Common Crawl index on Tranco top domains, together with Tranco homepages. The split prevents leakage, so the same site never appears in both train and test.

Preprocessing. IDNA and public-suffix aware normalisation. The scheme and credentials are removed from the model string (host[:port]/path?query), so "https" alone cannot make a URL look safe. Long URLs keep the first 191 and last 64 characters.

Models.

  • Hybrid char-CNN: 97-symbol embedding (32-d), parallel convolutions with kernel widths 3/5/7 (128 channels each), masked max-pooling, and a 27-feature structural branch (lengths, entropy, digits, IP host, punycode, user-info…), giving 416 → 64 → 1. 92,577 parameters.
  • Character 2–5-gram TF-IDF logistic regression with 300,000 terms.
  • Stacked calibrator fitted on 12,338 validation rows, with budgets of ≤0.5% false alarms and ≤5% missed phishing. It gives three outcomes: PHISHING (p > 0.683), LIKELY SAFE (p < 0.095), or UNCERTAIN.

Rules after the model: an exact match in the local threat list gives PHISHING; a known URL shortener gives UNCERTAIN (the app never expands it); a model-only PHISHING verdict on one of the top 1,000 popular sites is lowered to UNCERTAIN.

4.4 Combining results and explaining warnings

No extra "joint" model is trained. A transparent policy combines the results. If an SMS is low risk but contains a link classified as PHISHING, the message becomes high risk. A LIKELY SAFE link never clears SMS evidence. Every suspicious or high result immediately produces a factual note (What happened / What you can do) and a history entry.

A local Llama 3.2 1B Instruct model (SpinQuant INT4, ExecuTorch) then rewrites only the guidance into one sentence of 8–20 words (48-token cap). The output is checked for unsupported claims, prompt leakage and length. If generation fails, the default guidance remains. The LLM never sees raw SMS text, sender, OTP or full URL, and it cannot change the risk.

4.5 Android implementation

  • Kotlin app (Android SDK 34, Java 21 toolchain), Gradle multi-module: app, core (feature extraction shared with tests), test/lab modules.
  • Models are exported to ExecuTorch .pte files and run with the XNNPACK CPU backend. The linear models (TF-IDF LR, n-gram LR) are re-implemented in Kotlin from exported weights.
  • Foreground capture service (root) for the network detector; a broadcast receiver for new carrier SMS (multipart messages are re-assembled); share/paste screen for any other text or link.
  • The app verifies SHA-256 hashes of model files at load time. Native self-check fixtures confirm the phone gives the same output as the PyTorch reference.
  • Llama runs in an isolated worker process, so a crash or out-of-memory event cannot stop detection.
  • Seven-day, user-clearable history; "Expected repeat" feedback with Undo for known benign repeats.

Interpretation. The three detectors use very little hardware: a few milliseconds of one CPU core per event, under 100 MiB of resident memory, and no network access. 8. Privacy and safety design

  • No INTERNET permission in the APK: no cloud inference, no telemetry, and submitted URLs are never visited.
  • The SMS inbox is never read; only new carrier SMS (with user consent) or text the user shares or pastes.
  • History stores no raw SMS bodies, senders or OTPs. Saved links keep only the host, without path, query or credentials.
  • The LLM sees only approved facts and guidance, and its output is validated before display.
  • Every detector can be switched off independently. Network monitoring needs explicit root permission.
  • The public repository contains no datasets, private captures, messages, credentials or restricted feed snapshots.

9. Limitations

  • Network: normal SSH/FTP logins can be falsely flagged; distributed application-level DDoS and bot beacons were missed in live tests; the family label is often "Unclassified". The network detector needs a rooted phone.
  • SMS: the test set was used earlier in development, so it is a reused rather than a fresh hold-out. Coverage is mainly English; Hindi and code-mixed (Hinglish) messages were not separately evaluated. RCS, WhatsApp and other chat apps are only covered through share/paste.
  • URL: on the 2,048-URL phone file, only 218 URLs have independent labels, so full-file precision cannot be computed. The model judges the URL text only, not page content. The public build ships an empty threat database.
  • LLM: needs about 1.2 GiB RAM and a separate 1.06 GiB download. Cold start is slow (≈15 s), so it is optional.
  • A warning is a risk signal, not proof that the device is compromised. Rakshak does not block traffic automatically.

10. Future work

  • Collect more labelled phone traffic for authentication, DDoS and bot classes, and add session-level (episode) features to reduce login false positives.
  • Add Hindi and code-mixed (Hinglish) SMS data, and evaluate on a fresh, never-seen test set of real reported scams.
  • Build an independently labelled benign + phishing URL test set, and add optional user-approved feed updates.
  • Try NPU/GPU delegates (e.g., Android NNAPI/Tensor) for MobileBERT and Llama, and measure energy per request.
  • Support a VPN-based capture mode so that network detection works without root.

11. Conclusion

Rakshak shows that three different security detectors (network, SMS and URL) can run together on an ordinary Android phone without sending any data to the cloud. Careful feature alignment let a research network model work on real phone traffic. INT8 quantization and cascading made a transformer SMS classifier practical on-device with almost no accuracy loss. A combined CNN/n-gram URL detector checks links in about 4 ms. Showing facts first and letting a small local LLM only rephrase the guidance makes warnings understandable without letting the LLM decide anything. We have documented both successes and failures, and the open-source repository contains the code, models, evidence and instructions needed to reproduce and extend the work.

Install the app

  1. Download app-debug.apk from the repository's GitHub Releases / Actions artifacts, or build it: android/gradlew -p android :app:assembleDebug (Java 21, Android SDK 34).
  2. Install: adb install -r app-debug.apk, or open the APK on the phone.
  3. Open Rakshak, enable Automatically check incoming SMS and links, and grant SMS and notification permissions. Network monitoring additionally needs a rooted phone.
  4. Optional: download the Llama model as described in docs/ANDROID_SETUP.md.

Run the checks

pip install -r requirements.txt
python -m pytest tests -q
python -m unittest validation.test_url_benchmark_metrics
python reproduce.py paper --smoke

Continuous integration (GitHub Actions) runs the Python tests and a full Android build on every push. Full training needs the public datasets listed above; step-by-step commands are in REPRODUCE.md.
